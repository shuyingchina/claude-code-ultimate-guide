## 1. 一图看懂全景

两个轴向构建了这一版图：**与模型的距离**（你是在训练它、给它写提示词，还是在围绕它构建基础设施？）以及**与生产环境的距离**（研究 vs. 已上线产品）。

```
              ← Closer to the model          Closer to infrastructure →

Research    ML Engineer ←────────────────────────── AI Architect
            AI Safety Engineer                       Platform Engineer
                  │                                        │
                  │                                        │
Production   LLM Engineer ──── AI Engineer ──── AI Agent Engineer
             Context Engineer                    Harness Engineer
             Prompt Engineer                     Founding AI Engineer
                                                 AI Product Manager
```

大部分新增的岗位需求集中在**右下角**：构建能够上线、并在生产环境中持续稳定运行的可靠 AI 系统。"纯研究"象限依然竞争激烈且高度专业化。增长最快的是那些贴近应用、面向产品的角色。

## 2. Prompt Engineer（提示词工程师）

**现状**：第一波浪潮（2022-2023），部分已被商品化，但在专业化场景中仍有价值。

### 他们做什么

精心设计并优化发送给 AI 模型的指令，以获得可靠、高质量的输出。其工作范围从一次性提示词到面向生产系统的复杂多步提示链。

### 职责

- 为特定用例（客户支持、代码生成、文档分析）设计提示词模板
- 运行系统化的 A/B 测试以衡量提示词表现
- 整理提示词库并进行版本管理
- 针对成本优化提示词（更少的 token，同等质量）
- 与领域专家合作，将知识编码进提示词中

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| 理解 LLM 的行为与失败模式 | 与非技术利益相关者沟通 |
| 基础 Python（用于自动化与测试） | 系统化的实验思维 |
| 熟悉评测框架 | 关注边界情况 |
| 版本管理实践 | 文档纪律 |

### 走向何方

作为独立角色的 "prompt engineer" 头衔正在被整合进更宽泛的 AI Engineer 或 Context Engineer 角色中。它仍然存续的场景：那些拥有非常具体、高风险提示词领域的公司（法律、医疗、金融合规）。如果你正担任这一角色，建议向上下文工程或 AI 工程方向提升技能。

### 入行路径

技术文档撰写者、QA 工程师、领域专家（法律、医疗、金融）、内容策略师。

## 3. Context Engineer（上下文工程师）

**现状**：新兴角色 — 2025 年增长最快的专业方向之一。

### 他们做什么

上下文工程是提示词工程的演进。提示词工程师精心设计指令，而上下文工程师设计的是**系统** — 在正确的时间、以正确的格式，把正确的信息提供给 AI 模型。Andrej Karpathy 明确地从 "vibe coding" 的说法转向了 "context engineering"，认为后者是对这项工作更精确的描述。

完整的学科内容参见 [Context Engineering 参考文档](./context-engineering.md) — 包括 ACE 流水线（第 6 节）、L0→L5 成熟度模型（第 9 节），以及区分 Level 4 与 Level 5 系统的运作机制：信号分类法与因果归因（第 10 节）、基于 PR 的闭环（第 11 节）、休眠规则的剔除（第 12 节）、宪法式审计（第 13 节），以及多开发者画像的协调（第 14 节）。

> "上下文工程就是在正确的时间、以正确的格式，提供正确的信息和工具。" — Philipp Schmid，Google

### 职责

- 设计 RAG（检索增强生成）系统与知识库
- 在多轮交互和长周期任务中管理上下文窗口
- 定义智能体在任务执行过程中记住、检索或遗忘的内容
- 构建信息层级结构（system prompt、对话历史、检索到的文档、工具定义、安全约束）
- 同时针对准确性与成本优化上下文
- 通过系统化的评测衡量上下文质量

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| Python（上下文流水线自动化） | 系统性思维 |
| 向量数据库（Pinecone、Chroma、Weaviate） | 信息架构的直觉 |
| SQL 与 NoSQL（上下文检索） | 跨职能协作 |
| 云平台（AWS/Azure/GCP） | 好奇心与持续学习 |
| RAG 架构、嵌入模型 | 文档撰写的精确性 |

### 与其他角色的关系

上下文工程师处于 AI 工程师的上游（他们定义有哪些上下文可用），同时处于领域专家的下游（他们将领域知识编码为可检索的结构）。在大型组织中，他们与平台工程师密切相关。

### 入行路径

数据工程师、后端工程师、机器学习工程师、信息架构师。

## 4. AI Engineer（AI 工程师）

**现状**：主流角色 — 构建 AI 驱动产品的通才岗位。

### 他们做什么

构建端到端的 AI 系统。他们不是研究者（不从零训练模型），但也不仅仅是集成者。他们利用 LLM 和编排框架，构建能够上线的系统。可以把他们看作软件工程师，只不过在技术栈中额外加上了 LLM 集成、评测以及 AI 产品直觉。

### 职责

- 设计并实现 LLM 驱动的应用（聊天机器人、智能体、流水线）
- 构建评测框架以衡量模型输出质量
- 将 AI 能力集成进现有软件系统
- 在生产环境中监控 AI 系统（延迟、成本、质量漂移）
- 为特定任务选择合适的模型（能力 vs. 成本的权衡）
- 当基础模型不够用时，实施微调或 RAG

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| 扎实的软件工程基础 | 产品判断力 |
| Python（主力），JavaScript（常常需要） | 务实优先于研究上的纯粹 |
| 熟悉主流 LLM API（Anthropic、OpenAI、Gemini） | 快速迭代的思维 |
| 评测设计与度量 | 在需求模糊时也能推进工作的能力 |
| 理解嵌入、RAG、智能体框架 | 向利益相关者说明 AI 局限性的沟通能力 |
| MLOps 基础（部署、监控、版本管理） | |

### 与 ML Engineer 的关键区别

AI 工程师使用现有的模型。ML 工程师构建并训练模型。在实践中，2025-2026 年大多数公司招聘需要的是 AI 工程师（应用模型），而不是 ML 工程师（构建模型）。

### 入行路径

软件工程师（最常见）、后端工程师、数据工程师、转向应用工作的 ML 工程师。

## 5. LLM Engineer（大模型工程师）

**现状**：AI Engineer 的专业化变体，在以模型为核心的公司中尤为突出。

### 他们做什么

在大语言模型的集成与优化上深度专精。AI 工程师是通才，而 LLM 工程师则深入到模型层：微调、RLHF、模型选型、规模化的提示词优化，以及评测基础设施。

### 职责

- 针对领域特定任务微调基础模型
- 设计并运行系统化的模型评测（evals）
- 实现 RLHF 或类似的反馈机制
- 模型性能基准测试与回归测试
- 管理模型版本，并对新模型发布进行 A/B 测试
- 构建用于模型监控与漂移检测的工具

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| Python（熟练） | 科学严谨性 |
| PyTorch 或 JAX | 统计思维 |
| Transformers 架构知识 | 对缓慢反馈循环的耐心 |
| 评测框架设计 | 实验过程的文档记录 |
| 分布式训练基础 | |

### 走向何方

在 AI 公司（Anthropic、OpenAI、规模化创业公司）以及构建专有模型的大型企业中需求强劲。它与 AI 工程师的区别在于更贴近模型本身。预计这一角色会分化：实验室里的纯研究 vs. 企业中的应用型微调。

## 6. AI Agent 工程师

**现状**：高速增长——2025-2026 年最抢手的专业化角色之一。

### 他们做什么

设计并构建自主 agent 系统。AI 工程师构建通用 AI 产品，而 agent 工程师专注于能够规划、推理、使用工具并在无需人类持续干预的情况下执行多步任务的系统。

### 职责

- 设计多 agent 架构（编排器 + 专家 agent）
- 构建 agent 记忆系统（短期、长期、情景记忆）
- 为 agent 实现工具使用与 API 集成
- 为自主系统设计护栏与安全机制
- 为高风险决策构建 human-in-the-loop 检查点
- 在生产环境中监控 agent 行为（可靠性、成本、异常检测）
- 系统性地测试 agent 系统（agentic eval 是一门独立的学科）

### 必备技能

| 技术能力 | 软技能 |
|-----------|------|
| Agent 框架（LangChain、AutoGen、Claude Agent SDK、CrewAI） | 系统思维 |
| 编排模式 | 风险判断（何时让 agent 自主行动） |
| 工具/API 集成 | 用户体验直觉 |
| 异步编程 | 调试耐心（agent 以非确定性的方式失败） |
| 可观测性与追踪（LangSmith、Langfuse 等） | |

### 该角色特有的关键挑战

非确定性。Agent 系统会以难以复现的方式失败。可观测性工具（追踪每一个 agent 步骤）与 agent 代码本身同样关键。把 agent 调试当成传统代码调试来对待的工程师会很吃力。

## 7. Founding AI 工程师

**现状**：在 AI 原生初创公司以及种子轮到 A 轮的公司中极受青睐。

### 他们做什么

一种早期公司特有的混合角色：既是 AI 工程师，又是产品工程师，还是技术联合创始人。他们端到端地负责核心产品功能，从架构决策到客户交互，同时在 AI 能力之上进行构建。

> 通常面向 0-4 年经验的工程师，他们能从容应对模糊性、能独立摸索解决问题，并且已经在日常工作流中每天使用 AI 工具。

### 职责

- 构建完整的产品功能，从架构到部署，而不只是处理分派的工单
- 做出将在多年内塑造公司技术栈的基础性技术决策
- 直接与创始人就产品策略和优先级排序协作
- 把 AI 编码工具当作力量倍增器，以初创公司的速度交付
- 直接与早期客户互动，理解他们的问题
- 在工程文化固化之前定义它

### 这个角色的不同之处

所有权的范围与模糊性。大公司里的资深工程师在既定系统内工作。Founding 工程师则定义这些系统。杠杆在两个方向上都很巨大：好的决策会复利累积，糟糕的决策会变成难以摆脱的技术债。

### 必备画像

- 偏向行动而非分析瘫痪
- 能从容交付不完美的东西并迭代
- 兼具产品直觉与技术能力
- 已经熟练使用 AI 编码工具（Claude Code、Cursor、Copilot）
- 能在同一天内从基础设施切换到产品再切换到客户调研

### 入行路径

成熟公司里希望获得更多所有权的优秀中级工程师。常见来源：那些一直默默用 AI 工具构建副业项目的工程师。

## 8. AI 架构师

**现状**：高级/Staff 级别——在大型组织中新兴的角色。

### 他们做什么

在系统层面设计企业级 AI 系统。AI 工程师交付功能，而 AI 架构师定义多个团队所使用的模式、平台和决策框架。他们做出的技术选择，其他人要承受多年。

### 职责

- 定义 AI 技术策略与技术栈决策（用哪些模型、哪些框架、哪些供应商）
- 设计企业级 AI 参考架构
- 为 AI 系统的可观测性、安全性和治理设定标准
- 评估 AI 能力的自建 vs. 采购决策
- 确保 AI 系统具备可扩展性、成本效益和可审计性
- 在业务需求与技术 AI 实现之间架起桥梁

### 必备技能

- 在 AI/ML 技术栈各层（模型、基础设施、MLOps）的深厚经验
- 强大的沟通能力（向 C 级高管汇报、与法务/合规协作）
- 对云服务商 AI 产品的了解（AWS Bedrock、Azure OpenAI、Vertex AI）
- 安全与合规意识（GDPR、AI Act、SOC2）
- 大规模分布式系统的设计经验

### 入行路径

资深 AI 工程师 → Staff → 架构师。通常需要在 AI 相邻角色上花费 5-8 年。或者：云架构师 + 强力的 AI 自学。

## 9. 平台工程师（AI 语境）

**现状**：成熟角色，因 AI 而被显著重塑。

### 他们做什么

构建并维护内部开发者平台。在 AI 的加持下，这个角色已经扩展到包括 AI 开发的"黄金路径"：让团队集成 LLM 的标准化方式、通用的可观测性基础设施、成本管控以及护栏，从而让各个团队不必重复造轮子或制造安全风险。

### 在传统平台工作之上新增的 AI 专属职责

- 提供标准化的 LLM 集成模式（内部 SDK、代理、抽象层）
- 跨团队管理 API key、速率限制和成本分摊
- 构建 AI 可观测性基础设施（追踪、日志、告警）
- 对 AI 输出强制执行安全策略（PII 过滤、输出校验）
- 维护模型注册表和版本管理系统
- 为 RAG 模式、agent 架构、eval 流水线创建"铺好的路"

### 为什么这个角色在 AI 时代更重要

当每个团队都在构建自己的 LLM 集成时，你会得到：重复的成本、不一致的安全性、没有集中化的可观测性，以及没有共享的经验沉淀。懂 AI 的平台工程师能防止这种碎片化。正是因为他们，公司在 AI 上的投入才能规模化扩展，而不是四处蔓延。

### 必备技能（AI 增量部分）

MLOps 工具、LLM 网关产品（LiteLLM、Portkey）、云 AI 服务、成本优化模式、面向 AI 的安全（prompt injection 缓解、输出过滤）。

## 10. Harness 工程师

**现状**：新兴角色——由 Martin Fowler 于 2025 年正式提出，尚未作为独立头衔被制度化。

### 他们做什么

构建让 AI agent "处于约束之下"（under harness）——处于受控状态——的基础设施。随着 agentic AI 系统生成代码、采取行动并以越来越高的自主性运行，harness 工程师构建相应的系统，确保它们保持在架构约束之内、产出连贯的结果，并且不会随时间累积熵。

> 来源：[Martin Fowler — Harness Engineering](https://martinfowler.com/articles/exploring-gen-ai/harness-engineering.html)

### 三大支柱

**1. 上下文工程（知识基础设施）**
不是一次性的 prompt，而是一个嵌入代码库、持续更新的知识库。Agent 了解你的约定、架构决策和领域上下文。能动态访问可观测性数据和文档。

**2. 架构约束（agent 护栏）**
- 基于 LLM 的看门狗 agent，负责审查生成的代码
- 强制执行你特定架构模式的自定义确定性 linter
- 自动运行的结构性测试（ArchUnit 风格）
- 拒绝违反既定约束的代码的 pre-commit hooks

**3. 熵管理（漂移防控）**
周期性运行的 agent，扫描代码库以发现：过时的文档、悄悄溜过去的架构违规、又重新出现的废弃模式，以及多个 agent 并行工作引入的不一致。

### 核心洞见

没有 harness，AI agent 产出的代码单独看都没问题，但整体上会逐渐偏离你的架构、你的模式和你的文档。Harness 正是让"AI 生成大部分代码"在规模上可持续、而非通向无法维护系统的关键。

### 正式框架（arXiv 2605.18747，2026 年 5 月）

《Code as Agent Harness》（arXiv 2605.18747）将一个生产级 harness 必须满足的三条属性形式化。这些属性可作为在选择 harness 框架时、或评估一个内部工具链究竟是 harness 还是仅仅是 wrapper 时的评判标准。

**可执行性（Executability）。** Harness 真正运行模型产出的代码，并客观地验证结果。仅有文本或代码生成不算数。只校验语法但不校验行为的 harness 不满足这一属性。Anthropic SDK、OpenAI Agents SDK 和 LangGraph 各自实现了让可执行性变得具体的 while-loop 执行引擎。

**可检视性（Inspectability）。** Agent 采取的每一步都可被追踪，以便诊断和生成反馈。OpenInference（由 Arize 维护）和 OpenLLMetry（Traceloop）是在 OpenTelemetry 生态中标准化这一属性的两个埋点层。截至 2026 年 5 月，OTel GenAI SIG 将 `gen_ai.client` span 定义为稳定，将 `gen_ai.agent` span 定义为实验性。

**有状态性（Statefulness）。** Harness 在会话之间以及连续的工具调用之间维持连续性。没有有状态性，每次 agent 交互都从零开始，被迫重新发现已经建立过的上下文。E2B 和 Northflank 在基础设施层面实现这一点；Anthropic Claude Managed Agents 和 AWS Bedrock AgentCore 在产品层面实现这一点。

Martin Fowler 精准地总结了这一区别："原始模型不是 agent。当它连接到 harness 时，才成为 agent。" O'Reilly 将 harness 描述为"可靠 AI 系统的新前沿"（2026）。九个具体组件构成一个生产级 harness：while-loop 引擎、上下文管理、工具注册表、子 agent 管理、内置 skills、会话持久化、动态 prompt 组装、生命周期 hooks，以及权限强制执行。

### 组织影响

这个角色推动着**有意为之的技术收敛**：拥有 2-3 个主要技术栈的组织，从标准化 harness 中获益远多于拥有 10 个不同技术栈的组织。这是一笔用技术自由换取可靠性的有意权衡。

> "Ce n'est pas quelque chose dans lequel vous pouvez vous lancer pour des résultats rapides." — Martin Fowler

### 这个角色将在哪里出现

目前被以下角色吸收承担：平台工程师、staff/principal 工程师、架构公会（architecture guilds）。很可能在以下场景中成为一个明确的角色：

- 大规模运行自主编码 agent 的公司
- 拥有 50 名以上使用 AI 编码工具的工程师的大型企业
- 亲身经历过"AI 熵"的组织（代码能跑，但已经没人能看懂了）

### 必备技能

软件架构、linter/静态分析工具、LLM 编排、可观测性、代码库知识管理、熵检测模式。

## 11. AI 产品经理

**现状**：已成主流且持续增长，相比传统 PM 角色有显著溢价。

### 他们做什么

具备深厚 AI 素养的产品管理。他们理解 AI 能做什么、不能做什么，管理 AI 系统特有的产品挑战（非确定性、延迟、幻觉、成本），并在业务需求与 AI 能力之间做翻译。

### 职责

- 在考虑技术约束的前提下，为 AI 功能定义产品需求
- 与 AI 工程师一起制定评估标准（怎样才算"好"？）
- 管理 AI 特有的 UX 挑战：不确定性、延迟、错误处理
- 负责 AI 功能在成本/质量/速度之间的权衡
- 向利益相关者传达 AI 的局限与风险
- 针对模型版本、prompt 变更、功能变更运行 A/B 测试

### AI PM 与传统 PM 的不同之处

传统 PM 交付行为确定的功能。AI PM 交付输出会变化的系统。他们需要以概率方式思考：不是"这能行吗？"，而是"这有多大比例的概率能行，其余情况下会发生什么？"质量度量是持续的，而非二元的。

### 必备技能

标准 PM 技能（路线图规划、优先级排序、用户研究），外加：LLM API 熟悉度、eval 设计、能用基础 Python 跑实验、对模型权衡的理解（准确率 vs. 成本 vs. 延迟）、AI UX 模式。

### 薪资背景

FAANG 级别：入门级 AI PM 为 16 万-20 万美元以上。资深：总薪酬 20 万-30 万美元以上。

## 12. AI 安全与评估工程师（AI Safety & Eval Engineer）

**现状**：专业岗位 — 主要存在于 AI 实验室以及部署受监管 AI 的公司。

### 他们做什么

确保 AI 系统的行为安全、可靠，并与既定价值观保持一致。这包含两个相关但各有侧重的专业方向：**评估工程师（Eval Engineers）**（构建衡量模型行为的系统）和 **AI 安全工程师（AI Safety Engineers）**（识别并缓解 AI 系统中的风险）。

### 评估工程师的职责

- 设计评估框架（evals）以衡量模型的质量、安全性和能力
- 构建自动化评估流水线，在每次模型版本变更时运行
- 定义能够捕捉真实世界表现的指标（而非仅仅刷榜）
- 为主观质量维度实现人工评估工作流
- 在回归问题进入生产环境之前将其检出

### AI 安全工程师的职责

- 对 AI 系统进行红队测试，找出失效模式、越狱手法和有害输出
- 实现内容过滤、输出校验和护栏系统
- 为高风险决策设计 human-in-the-loop 检查点
- 监控生产系统的有害输出或异常行为
- 与法务/合规团队协作开展 AI 治理

### 所需技能

严谨的实验设计、统计学、Python、对 LLM 失效模式的深刻理解，以及用于风险报告的沟通能力。

### 在哪里能找到这些岗位

主要集中在：Anthropic、OpenAI、Google DeepMind、Meta AI、Microsoft AI。在以下领域增长中：医疗、金融、法律科技 — 这些受监管行业中 AI 错误会带来严重后果。

## 13. ML 工程师（ML Engineer）

**现状**：成熟岗位 — AI 工程岗位中最传统的一种。

### 他们做什么

开发、训练、部署并维护机器学习模型。在 LLM 时代，许多 ML 工程师已转向微调和应用型 AI 工作，而非从零构建模型 — 后者越来越集中在少数几家前沿实验室。

### 职责

- 数据流水线开发（采集、清洗、转换）
- 模型训练与微调
- 特征工程
- 模型服务与部署（MLOps）
- 性能优化与模型压缩
- 针对模型漂移的生产监控

### 这个角色如何演变

除前沿实验室外，"从零构建模型"的路径越来越罕见。如今大多数公司的 ML 工程师从事的是：对现有模型进行微调、构建 RAG 系统、在生产中部署和监控模型，以及在 AI 工程师与数据基础设施之间搭建桥梁。与 AI 工程师在实际工作中的重叠度很大。

### 所需技能

Python（熟练）、PyTorch 或 TensorFlow、分布式计算、数据流水线工具（Spark、Airflow、dbt）、云 ML 平台（SageMaker、Vertex AI、Azure ML）、统计学基础。

## 14. MLOps 工程师（MLOps Engineer）

**现状**：成熟岗位 — 区别于 ML 工程师，在大规模部署模型的企业中不断增长。

### 他们做什么

弥合模型开发与生产基础设施之间的鸿沟。ML 工程师构建和微调模型、AI 工程师构建应用，而 MLOps 工程师负责运维层：模型的 CI/CD 流水线、部署基础设施、漂移与退化监控，以及让模型长期可靠运行于生产环境的各类系统。

### 职责

- 构建并维护用于模型训练、评估和部署的 CI/CD 流水线
- 监控生产模型的性能漂移、数据漂移和预测质量退化
- 设计特征存储（feature store）和模型注册表（model registry）
- 为新模型版本实现 A/B 测试和金丝雀部署
- 管理训练和推理的算力基础设施（成本优化）
- 构建可观测性工具：针对模型生产行为的指标、日志和告警
- 建立模型版本管理与回滚流程

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| Python（熟练） | 基础设施思维 |
| 云 ML 平台（SageMaker、Vertex AI、Azure ML） | 跨团队协作（ML + Infra） |
| Kubernetes、Docker、基础设施即代码 | 可靠性工程直觉 |
| MLflow、Weights & Biases 或类似的实验追踪工具 | 事件响应纪律 |
| 数据流水线工具（Airflow、Prefect、dbt） | |
| 监控与可观测性（Prometheus、Grafana） | |

### 关键区别

ML 工程师问的是："模型能用吗？" MLOps 工程师问的是："模型能持续可用吗？" 模型的运维生命周期 — 监控、再训练触发条件、回滚流程、单次推理成本 — 与构建模型本身完全是两回事。跳过这个角色的公司，往往要等到模型在生产中悄然退化、直到用户投诉激增才发现问题。

### 入门路径

补充了 ML 知识的 DevOps/平台工程师、倾向于基础设施方向的 ML 工程师、转向模型运维的数据工程师。

## 15. AI 开发者布道师（AI Developer Advocate）

**现状**：高速增长 — 2025-2026 年各大 AI 公司均在积极招聘。

### 他们做什么

在 AI 平台与使用该平台的开发者之间搭建桥梁。半个工程师、半个教育者、半个社区建设者。他们在技术上钻得足够深，能用平台真正构建出东西，再把这些知识转化为教程、文档、示例项目和公开影响力，帮助其他开发者获得成功。

### 职责

- 使用平台的 API 构建技术演示、示例项目和集成
- 创作开发者内容：教程、博客文章、视频讲解、大会演讲
- 向产品和工程团队反映开发者的需求与痛点
- 与开发者社区互动（Discord、GitHub、论坛、社交媒体）
- 在大会上演讲并主持工作坊
- 帮助战略合作伙伴和企业开发者完成接入
- 收集并提炼开发者反馈，转化为产品改进

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| 扎实的软件工程基础 | 清晰的技术写作能力 |
| 对平台/API 的深入熟悉 | 公开演讲的自信 |
| 快速构建示范性原型的能力 | 社区直觉 |
| 对开发者体验（DX）的理解 | 对困惑用户的同理心 |
| 熟悉 AI 概念（prompting、RAG、agents） | 好奇心与持续学习 |

### 这个角色的不同之处

受众是其他开发者，而非终端用户。DevRel 的成功以开发者激活度（开发者会去试用产品吗？）、留存率（他们会持续使用吗？）和拥护度（他们会推荐给别人吗？）来衡量。可信度是核心资产 — 这意味着你必须真正构建东西，而不只是空谈。一个从未用平台交付过真实生产代码的 DevRel，在其目标受众面前毫无可信度可言。

### 薪资背景

基础薪资 $120K-$180K（美国），资深/主管岗位 $150K-$250K+。在多数 AI 公司，总薪酬还包含股权。

### 这些岗位在哪里

正在积极招聘：Anthropic、OpenAI、Together AI、Mistral、Cohere、Hugging Face、LangChain，以及任何构建面向开发者 AI 产品的公司。随着企业软件公司加入 AI 能力、需要有人帮助开发者采用这些能力，该角色正从 AI 实验室向外扩展。

### 入门路径

具备公开影响力（博客、开源、大会演讲）的软件工程师、有工程背景的技术写作者、在公开场合构建作品的早期 AI 社区成员。

## 16. AI 编排工程师（AI Orchestration Engineer）

**现状**：新兴岗位 — 2025 年已出现真实招聘信息，在职责范围上区别于 AI 智能体工程师。

### 他们做什么

设计并构建智能工作流，将 AI 能力与现有系统、数据源和业务流程连接起来。如果说 AI 智能体工程师构建的是自主推理系统，那么 AI 编排工程师专注的是集成层：将 AI 接入企业工具、设计多步骤自动化流程，并让 AI 能够在现有基础设施中可靠地运转。

### 职责

- 使用编排工具（n8n、LangChain、Power Automate、Zapier）设计端到端的自动化架构
- 将 AI 能力与 CRM、ERP、数据仓库和通信平台集成
- 为企业知识系统构建检索与综合栈（RAG + 答案溯源）
- 定义工作流可靠性模式：重试、降级、人工升级触发条件
- 为编排工作流搭建可观测性（追踪每一步、成本追踪）
- 在横跨工程、产品和业务领域团队的跨职能系统中将 AI 投入实际运营

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| 编排平台（n8n、LangChain、LlamaIndex） | 流程分析 |
| API 集成（REST、GraphQL、webhooks） | 跨职能协作 |
| Python 或 JavaScript（工作流脚本） | 系统思维 |
| 数据转换与映射 | 业务流程直觉 |
| 可观测性与追踪（LangSmith、Langfuse） | |

### 与 AI 智能体工程师的区别

| AI 智能体工程师 | AI 编排工程师 |
|-------------------|--------------------------|
| 构建自主推理系统 | 构建将 AI 连接到现有系统的集成工作流 |
| 重点：规划、记忆、多步推理 | 重点：连通性、可靠性、流程自动化 |
| 核心挑战：非确定性 | 核心挑战：集成复杂度 |
| 主要面向产品 | 主要面向内部/企业 |

### 这个角色在招聘信息中如何出现

职位名称差异很大："AI-First Orchestration Engineer"（Vista Equity Partners）、"Staff AI Engineer (Orchestration)"（Heidi Health）、"Sr. Software Engineer (AI Orchestration Zone)"（Zapier）、"AI Engineer, AI Orchestration"（Adobe）。即便名称各异，其职能是一致的。

### 入门路径

集成工程师、有工作流自动化经验的后端工程师、补充了 AI 工具能力的 DevOps 工程师、转向写代码的业务流程自动化专家。

## 17. 规格工程师（Spec Engineer）

**现状**：2026 年新兴岗位，随规格驱动开发（Spec-Driven Development）的普及而增长。

### 他们做什么

编写供 AI 智能体用于规划、实现和验证代码的结构化规格说明。随着各组织在 Shapiro 量表上从 L2（助手）迈向 L3（受编排的智能体），规格质量成为产出质量的首要决定因素。规格工程师是智能体时代的"需求分析师"：他们在业务意图与机器可执行的契约之间架起桥梁。

### 核心职责

编写同时满足三个条件的规格说明：足够精确，使智能体能据此生成正确代码；足够易读，使产品经理能审批通过；足够稳定，能在实现发生偏移时充当可供 diff 对比的事实基准。

GitHub Spec Kit 将其形式化为一条四阶段流水线（Constitution、Specify、Plan、Tasks），其中位于 `.specify/` 中的规格文件即为治理性产物。Factory.ai 的 Missions 对此做了扩展，要求在任何实现开始之前就写好行为验证契约。在一个 Slack 克隆项目中，独立的验证器智能体仅凭规格就发现了 81 个问题，由此产生的"修复特性"占了整体实现工作量的 34%。

### 所需技能

| 技术能力 | 软技能 |
|-----------|------|
| 结构化写作（Gherkin 风格的 Given-When-Then 或等价形式） | 在模糊中保持精确 |
| 理解智能体失效模式（无规格时多文件任务的 pass@1 仅为 19.4%） | 同时与产品、工程和 LLM 进行协商 |
| 熟悉 SDD 工具（Spec Kit、Kiro、Augment、Factory.ai） | 能区分规格必须约束什么、应当留白什么 |
| 版本控制纪律（规格先于代码进行版本管理） | |

### 入门路径

有工程背景的技术写作者、理解需求的 QA 工程师、因 AI 输出信噪比过低而苦恼的产品工程师、转向 AI 相关工作的业务分析师。

## 18. Agent Identity Architect（智能体身份架构师）

**状态**：关键缺口。截至 2026 年，77% 的组织没有正式的智能体身份策略。

### 他们做什么

设计并落实 AI 智能体的身份层：智能体如何向服务进行认证、它们持有哪些权限、这些权限如何被限定范围并接受审计，以及当智能体跨服务串联工具调用时如何防止权限提升。

### 为什么这个角色如今会出现

致命三要素（Lethal Trifecta，Simon Willison，2025）：访问私有数据 + 暴露于不可信内容 + 具备对外通信能力 = 有据可查的数据外泄途径。大多数组织都理解这一威胁，却尚未构建防御。Strata Identity Research 2026 显示，44% 的组织仍在使用静态 API key 进行智能体认证，23% 拥有正式策略，18% 依赖 IAM 信任继承且没有针对单个智能体的范围限定。

### 这个角色涵盖的内容

- **每个智能体专属的服务主体**：Microsoft Entra Agent ID 提供专用的服务主体类型，配合限定到特定会话上下文的 OAuth On-Behalf-Of（OBO）流程。不是共享的 API key，也不是团队凭据。
- **MCP 网关治理**：每一次 MCP 工具调用都会经过一个身份实施点，该点会对照当前任务范围校验发起调用的智能体的权限。
- **会话追踪**：每一个动作都可归因到特定的智能体会话，而不仅仅是"那个 AI 系统"。
- **权限提升防护**：由编排器生成的子智能体默认无法继承父级权限；它们只获得完成任务所需的最小范围。

### 所需技能

IAM 与 OAuth/OIDC 专长、零信任架构、Kubernetes RBAC、对 MCP 安全模型的理解、针对非确定性系统的事件响应。

### 入门路径

云安全工程师、身份/访问管理专家、专注于安全方向的平台工程师。

## 19. AI Eval Engineer（AI 评测工程师）

**状态**：与 AI Safety & Eval（第 12 节）有所不同。这个角色聚焦于生产环境的度量，而非实验室安全。

### 他们做什么

构建并运营持续度量层，让组织得以判断其 AI 系统是在变好还是变差。不是红队测试（那是 AI Safety），也不是微调（那是 LLM Engineer）。纯粹是度量：随着时间推移、跨越模型升级、跨越流量分布变化，输出质量是否依然稳定？

### 他们解决的结构性问题

Anthropic 自己的数据显示，生产环境中 93% 的权限请求在缺乏充分审查的情况下被批准。JudgeBiasBench（arXiv 2604.23178）记录到，LLM-as-judge 系统的风格偏差得分为 0.76-0.92，真负率低于 25%，这意味着它们会批准大多数错误的输出。这两个事实放在一起说明，仅依赖人工审查与 LLM-as-judge 并不是一种质量策略。Eval Engineer 构建第三层：具备明确通过/失败标准的结构化评测流水线，不依赖于人的注意力，也不依赖 LLM 的批准偏差。

### 职责

- 设计带有明确指标（任务完成率、工具正确率、幻觉率）的评测框架
- 构建金丝雀流水线，在推广模型变更之前先对 1-2% 的生产流量运行 A/B 对比
- 为高风险工作流实现 creator-verifier 模式（由独立智能体检查智能体的输出）；相比自我验证，独立验证可将正确率提升 +12% 至 +26%
- 监控静默退化：模型更新后代码生成质量下降却没有触发任何告警
- 维护不会过拟合当前模型倾向的评测基准

### 所需技能

统计实验设计、Python、对 LLM 失败模式与偏差模式的理解、CI/CD 流水线集成、对 OTel GenAI 约定的工作级了解（截至 2026 年 5 月，gen_ai.client span 已稳定，gen_ai.agent span 仍处于实验阶段）。

### 工具

Arize Phoenix（生产环境每月 1 万亿条 span，可自托管 ELv2）、Langfuse（OTel 原生 v3，MIT 开源）、DeepEval（Python 原生的 pytest 集成）、LangWatch Scenario SDK（多轮模拟）、AWS Bedrock AgentCore（对 1-2% 的实时流量做评测）。

## 22. 哪些还不算一个角色（暂时）

有些你会听到的术语描述的是实践或方法论，而非职位头衔：

**Vibe coder** —— 一种方法论（让 AI 编码助手处理实现，而你专注于设计），而非一份工作。Andrej Karpathy 创造了这个词，随后他自己转向了更精确的"context engineering"。没有任何正经公司会在职位描述里写"Vibe Coder"。

**AI-native engineer** —— 描述的是对所有工程师日益普遍的一种素质要求，而非一个专门角色。它的意思是：你在日常工作流中能熟练使用 AI 工具。它是门槛，而非头衔。

这些术语值得了解（你会在职位描述和文章中遇到它们），但它们暂时还不代表独立的职业路径。
